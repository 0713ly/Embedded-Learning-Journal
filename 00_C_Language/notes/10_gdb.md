# 1. 单步执行和跟踪函数调用

本节通过一个实例，介绍如何使用 GDB 进行源码级调试，包括单步执行、进入函数、查看调用栈和变量，以及动态修改程序状态。

## 1.1 引入：一个诡异的 Bug

看下面的程序：
```c
#include <stdio.h>

int add_range(int low, int high)
{
    int i, sum;
    for (i = low; i <= high; i++)
        sum = sum + i;
    return sum;
}

int main(void)
{
    int result[100];
    result[0] = add_range(1, 10);
    result[1] = add_range(1, 100);
    printf("result[0]=%d\nresult[1]=%d\n", result[0], result[1]);
    return 0;
}
```
预期结果：从 1 加到 10 是 55，从 1 加到 100 是 5050。
实际运行结果：
```text
result[0]=55
result[1]=5105
```
**现象分析**：同一个函数，第一次调用正确，第二次调用错误。这说明**代码逻辑大概率没问题，而是“数据”出了问题**。由于两次调用的环境不同，导致错误的数据导致了错误的结果。

## 1.2 准备调试环境

在编译时**必须加上 `-g` 选项**，生成的可执行文件才能用 `gdb` 进行源码级调试：
```bash
$ gcc -g main.c -o main
$ gdb main
```
*   `-g` 选项的作用是在可执行文件中加入源代码的信息（如机器指令对应的源码行号），**并不是把整个源文件嵌入其中**。因此在调试时，必须保证 `gdb` 能在当前目录下找到源文件。
*   如果源文件被改名或移动，使用 `list` 命令会报错找不到文件。

## 1.3 GDB 基本查看命令

进入 `gdb` 后，提示符为 `(gdb)`。此时处于一个类似 Shell 的命令行环境中。

*   **查看帮助**：`help` 查看命令类别，`help files` 查看某类下的具体命令。
*   **查看源码**：
    *   `list`（简写 `l`）：从第一行开始列出源代码，每次列出 10 行。
    *   **直接回车**：重复上一条命令（会继续列出下 10 行代码）。
    *   `list 行号`：从指定行开始列出源码。
    *   `list 函数名`：列出特定函数的源代码。
*   **退出**：`quit`（简写 `q`）。

## 1.4 单步执行与跟踪函数

*   `start`：开始执行程序，并**停在 `main` 函数的第一条语句之前**等待命令。
*   `next`（简写 `n`）：执行下一行语句。**如果遇到函数调用，不会进入函数内部**，而是把整个函数当作一行执行完。
*   `step`（简写 `s`）：执行下一行语句。**如果遇到函数调用，则会进入函数内部**，停在函数体的第一行。

**调试过程**：
1. 用 `start` 启动，停在 `main` 函数。
2. 用 `n` 执行赋值语句，发现没报错但结果不对。
3. 使用 `start` 重新开始，这次用 `s` 命令钻进 `add_range` 函数内部观察。

## 1.5 查看函数调用栈与局部变量

当使用 `s` 进入函数后，可以通过以下命令查看当前所处的状态：

*   `backtrace`（简写 `bt`）：查看各级函数调用及参数。输出会显示当前的栈帧（Stack Frame）编号，`#0` 表示当前正在执行的函数，`#1` 表示调用它的上级函数。
*   `info locals`（简写 `i locals`）：查看当前栈帧的局部变量的值。
*   `frame 帧编号`（简写 `f 帧编号`）：切换到指定的栈帧。可以配合 `info locals` 查看上级函数（如 `main`）的局部变量。

## 1.6 定位并修复 Bug

在第二次调用 `add_range(1, 100)` 时，使用 `s` 进入函数，并用 `i locals` 查看局部变量：
```text
(gdb) i locals
i = 11
sum = 55
```
**破案了**：局部变量 `sum` 没有初始化。因为函数调用是**挨着**的（第一次调用完紧接着调用第二次），局部变量在栈空间的位置没变，第一次调用结束时 `sum` 的遗留值 `55` 被第二次调用继承了。`i` 从 11 开始循环，`sum` 从 55 开始累加，最终结果就是 5105。

**原因**：未初始化的局部变量具有不确定的值（内存垃圾数据）。

## 1.7 动态修改变量并继续调试

找到原因后，如果不想退出 GDB 重新编译，可以直接在 GDB 中修改变量的值：

*   `set var 变量名=值`：修改当前变量的值。例如 `set var sum=0`。
*   `finish`：连续运行当前函数直到返回，然后停下来等待命令。可以用它快速查看函数返回值。
*   `print 表达式`（简写 `p`）：打印表达式的值。其实质是执行表达式并打印结果。甚至可以用它来修改变量或调用函数：`p sum=0` 或 `p printf("...", ...)`。

## 1.8 GDB 基本命令速查表

| 命令 | 描述 |
| :--- | :--- |
| `backtrace` (或 `bt`) | 查看各级函数调用及参数（栈帧） |
| `finish` | 连续运行到当前函数返回为止，然后停下来等待命令 |
| `frame` (或 `f`) 帧编号 | 选择栈帧 |
| `info` (或 `i`) `locals` | 查看当前栈帧局部变量的值 |
| `list` (或 `l`) | 列出源代码，接着上次的位置往下列，每次列10行 |
| `list 行号` | 列出从第几行开始的源代码 |
| `list 函数名` | 列出某个函数的源代码 |

# 2. 断点

通过之前的学习，我们掌握了单步执行（`step`/`next`）。但如果代码很长，且错误发生在循环或函数的深处，单步执行会极其低效。此时，我们需要用到**断点（Breakpoint）**，让程序全速运行，直到特定位置才停下来。

## 2.1 引入：一个累加器未清零的 Bug

看下面的程序：
```c
#include <stdio.h>

int main(void)
{
    int sum = 0, i = 0;
    char input[5];

    while (1) {
        scanf("%s", input);
        for (i = 0; input[i] != '\0'; i++)
            sum = sum * 10 + input[i] - '0';
        printf("input=%d\n", sum);
    }
    return 0;
}
```
**程序功能**：将输入的字符串数字（如 `"234"`）转换为整型数字并累加打印。
**Bug 现象**：
第一次输入 `123`，打印 `input=123`（正确）。
第二次输入 `234`，打印 `input=123234`（错误，预期应该是 `234`）。

原因很明显：`sum` 变量在 `while` 循环内**没有重新初始化为 0**。第一次循环结束后，`sum` 变成了 123，第二次循环在此基础上继续累加。但在复杂的程序中，我们往往很难一眼看穿这类问题。这就需要借助 `gdb`。

## 2.2 跟踪变量：`display` 命令

既然怀疑是 `sum` 变量的问题，我们可以用 `display` 命令让它每次停下来时，都自动打印当前的 `sum` 值。

*   **`display 变量名`**：跟踪查看某个变量的值，每次程序暂停时都会显示。
*   **`undisplay 跟踪显示号`**：取消跟踪。每个 `display` 都会分配一个编号（如 `1: sum = ...`），使用 `undisplay 1` 即可取消。

```text
(gdb) display sum
1: sum = -1208103488  // 初始值不确定
(gdb) n
9           scanf("%s", input);
1: sum = 0            // 执行完 int sum = 0 后
(gdb) n
123                   // 输入 123
10          for (i = 0; input[i] != '\0'; i++)
1: sum = 0
```

## 2.3 设置断点与连续运行

如果你不想一步步走完没有问题的循环，可以使用 **`break`**（简写 `b`）命令在特定位置设置断点。

*   **`break 行号`**：在当前源文件的某一行设置断点。例如 `b 9`。
*   **`break 函数名`**：在某个函数开头设置断点。
*   **`continue`（简写 `c`）**：从当前位置开始**连续运行**程序，直到遇到下一个断点或程序结束。

**调试过程**：
1. 在第 9 行（`scanf` 处）设置断点：`(gdb) b 9`
2. 运行程序：`(gdb) c`
3. 输入 `123` 后，程序会执行完循环，再次回到第 9 行停住。
4. 此时输入 `n`，输入 `234`，然后往下执行，查看 `sum` 的值，发现 `sum = 123`。**Bug 暴露**：新的一轮循环没有把 `sum` 归零！

> ? **调试心法**：断点加单步，是使用调试器的基本方法。先用断点快速跳过没问题的代码，在怀疑的地方停下，再用单步慢慢走、慢慢分析。

## 2.4 断点的管理与控制

当一个项目中设置了多个断点时，我们需要进行管理：

*   **`info breakpoints`（简写 `i b`）**：查看当前设置的所有断点信息（包含编号、位置、是否启用等）。
*   **`delete breakpoints 断点号`**：删除指定编号的断点。如果直接输入 `delete breakpoints` 会提示是否删除所有断点。
*   **`disable 断点号`**：禁用某个断点（但保留它）。程序运行到该行时不会停下。
*   **`enable 断点号`**：重新启用某个断点。

## 2.5 条件断点

有时候循环次数太多，我们只想在满足某个条件时让程序停下来。
*   **`break 行号 if 条件`**：设置条件断点。例如，`b 9 if sum != 0`，意思是程序运行到第 9 行时，只有当 `sum` 不等于 0 时才会触发中断。
*   **`run`（简写 `r`）**：从头开始连续运行程序。

## 2.6 GDB 基本命令复习表

| 命令 | 描述 |
| :--- | :--- |
| `break` (或 `b`) `行号` | 在某一行设置断点 |
| `break 函数名` | 在某个函数开头设置断点 |
| `break ... if ...` | 设置条件断点 |
| `continue` (或 `c`) | 从当前位置开始连续运行程序 |
| `delete breakpoints 断点号` | 删除断点 |
| `display 变量名` | 跟踪查看某个变量，每次停下来都显示它的值 |
| `disable breakpoints 断点号` | 禁用断点 |
| `enable 断点号` | 启用断点 |
| `info` (或 `i`) `breakpoints` | 查看当前设置了哪些断点 |
| `run` (或 `r`) | 从头开始连续运行程序 |
| `undisplay 跟踪显示号` | 取消跟踪显示 |

## 2.7 课后习题解析

**题目**：分析下面字符串反转程序的 Bug。
```c
#include <stdio.h>

int main(void)
{
    int i;
    char str[6] = "hello";
    char reverse_str[6] = ""; // 全部初始化为 '\0'

    printf("%s\n", str);
    for (i = 0; i < 5; i++)
        reverse_str[5-i] = str[i];
    printf("%s\n", reverse_str);
    return 0;
}
```
**运行结果**：第一行打印 `hello`，第二行什么都没打印。

**Bug 原因**：
1. 循环 `i=0` 时，`reverse_str[5] = str[0]`，即 `'h'`。
2. 循环 `i=1` 到 `4` 时，依次把 `'e'`, `'l'`, `'l'`, `'o'` 存入 `reverse_str[4]` 到 `reverse_str[1]`。
3. **致命错误**：`reverse_str[0]` 从来没有被赋值过，它依然是初始化时的 `'\0'`（Null 字符）。
4. 当执行 `printf("%s\n", reverse_str);` 时，`printf` 遇到数组第一个元素 `reverse_str[0]` 就是 `'\0'`，它会认为这是一个空字符串，所以什么都不打印。

**正确写法**：
```c
for (i = 0; i < 5; i++)
    reverse_str[i] = str[4-i]; // 从 str 的末尾往前取字符
reverse_str[5] = '\0'; // 确保字符串正确结尾
```
*(或者使用指针交换首尾字符，等学完指针后再尝试)*


# 3. 观察点

我们在上一节修复了 `sum` 未初始化的问题，但这依然掩盖不了 `scanf("%s", input)` 带来的致命安全隐患：**数组越界**。

## 3.1 引入：数组越界与内存踩踏

代码中数组定义为 `char input[5];`。当我们输入一个超长的字符串（如 `"12345"`）时：
*   数组最多只能容纳 5 个字节，而 `"12345"` 加上自动添加的 `\0` 需要 6 个字节。
*   `scanf` 并不会检查目标数组的大小，它会直接把第 6 个字节（`\0`）写到数组外部的内存区域。
*   运行程序时，输入 `12345`，结果输出了诡异的 `input=123407`。

## 3.2 观察点（Watchpoint）

对于不知道某个内存单元是在哪里被修改的情况，**断点**就不够用了。此时需要用到**观察点**。
*   **断点**：当程序执行到某一行代码时中断。
*   **观察点**：当程序**访问或修改某个存储单元**时中断。

**使用命令**：
*   `watch 变量名/表达式`：设置观察点。例如 `(gdb) watch input[5]`。
*   `info watchpoints`（简写 `i watchpoints`）：查看当前设置的所有观察点。

**调试过程**：
1. 设置观察点 `watch input[5]` 后继续运行。
2. GDB 会打印出 `Old value` 和 `New value`，并停留在修改该内存单元的代码行。
3. 反复单步执行，你会发现 `input[5]` 的值每次都在递增：`0` -> `1` -> `2` -> ...
4. **真相大白**：局部变量 `i` 的存储单元在栈上紧挨着数组 `input`，由于越界，`input[5]` 实际上就是变量 `i` 的地址。`i++` 导致 `input[5]` 改变，而 `input[5]` 的变化又反过来影响了循环条件（本该是 `\0` 的地方变成了数字），导致循环无法正常结束，引发“内存踩踏”。

## 3.3 查看内存：`x` 命令

为了更清晰地看到底层内存状态，可以使用 `x` 命令（eXamine）。
*   **格式**：`x/数量格式 地址`
*   **示例**：`(gdb) x/7b input`
    *   `/7b` 表示打印 7 个单元，格式为 `b`（byte，按字节打印）。
    *   输出结果会以十六进制显示。前 5 个字节是 `input` 的字符，第 6 个字节就是越界被修改的 `\0`（实际上变成了 `0x04` 或 `0x05`）。
*   *注：最左边的一长串数字是内存地址，目前可以不用深究。*

## 3.4 表面修补与安全隐患

即使你发现了越界，但为了“赶紧跑通”，可能会在循环中加入数字检查：
```c
if (input[i] < '0' || input[i] > '9') {
    printf("Invalid input!\n");
    sum = -1;
    break;
}
```
这看起来似乎把非数字和超长输入都“拦截”了，但这只是**治标不治本**。因为内存已经被越界写坏了，变量 `i` 或 `input` 在底层已经被破坏，随时可能在后续的其他逻辑中引发新的、更难查的 Bug。`scanf` 的越界写入是底层的严重缺陷，必须使用更安全的函数（如 `fgets`）或限制读取长度来解决。

## 3.5 GDB 基本命令（3）

| 命令 | 描述 |
| :--- | :--- |
| `watch` | 设置观察点 |
| `info` (或 `i`) `watchpoints` | 查看当前设置了哪些观察点 |
| `x` | 从某个位置开始打印存储单元的内容，全部当成字节来看，而不区分哪个字节属于哪个变量 |


# 4. 段错误

如果程序运行时出现段错误（Segmentation fault），用 `gdb` 可以很容易定位到究竟是哪一行引发的段错误。

## 4.1 快速定位段错误（例 10.4）

看下面这个简单的程序：
```c
#include <stdio.h>

int main(void)
{
    int man = 0;
    scanf("%d", man); // 错误：漏写了 &
    return 0;
}
```

**调试过程**：
1. 在 `gdb` 中运行 `(gdb) r`，输入数据后程序崩溃：`Program received signal SIGSEGV, Segmentation fault.`
2. 提示错误发生在 `_IO_vfscanf` 函数中。
3. 使用 **`bt`** 命令查看调用栈，可以看到 `_IO_vfscanf` 是被 `scanf` 调用的，而 `scanf` 是在 `main.c` 的第 6 行被调用的。
4. **结论**：`scanf` 要求传入变量的**地址**，而这里直接传了变量 `man` 的值（0）。`scanf` 试图将读取的数据写入内存地址 0，从而引发了非法的内存访问，导致段错误。

## 4.2 隐蔽的段错误：函数返回时才崩溃（例 10.5）

考虑上一节的代码，加入了 `if` 判断非法字符，并去掉了外层的 `while(1)` 循环（只执行一次转换）：
```c
#include <stdio.h>

int main(void)
{
    int sum = 0, i = 0;
    char input[5];

    scanf("%s", input);
    for (i = 0; input[i] != '\0'; i++) {
        if (input[i] < '0' || input[i] > '9') {
            printf("Invalid input!\n");
            sum = -1;
            break;
        }
        sum = sum * 10 + input[i] - '0';
    }
    printf("input=%d\n", sum);
    return 0;
}
```
*   如果输入超长字符串 `"1234567890"`，程序会触发 `if` 条件，打印 `Invalid input!`，看起来正常。
*   但如果输入**更长的字符串**，如 `"1234567890abcdef"`，程序会先报错，**紧接着发生段错误**。

**调试过程**：
*   用 `gdb` 运行并报错后，`gdb` 提示段错误发生在第 19 行：`19 }`。
*   第 19 行是 `main` 函数的结束括号，这行代码什么也没有，为什么会报错？

**重要规律**：
> **如果某个函数的局部变量发生访问越界，有可能并不立即产生段错误，而是在函数返回时产生段错误。**

**原理解释**：
局部变量（如 `input` 数组）分配在栈（Stack）上。当输入严重越界时，会向上“踩踏”栈帧结构。如果踩坏了保存的寄存器状态（如 `EBP`）或**函数的返回地址**，当函数执行完 `return 0;` 准备退栈返回时，CPU 会跳转到一个非法的内存地址，从而触发段错误。

## 4.3 为什么需要学习底层原理？

作者在此强调，写出无 Bug 的程序非常不易，即使是 `scanf` 这样简单的函数，也隐藏着各种玄机。很多初学者常有的疑问：
1.  为什么变量 `i` 的存储单元紧紧跟在 `input` 数组后面？
2.  为什么同样是访问越界，有时出段错误有时不出？
3.  为什么 `scanf` 读取整型变量必须要加 `&`，而读取字符串（数组名）却不要 `&`？
