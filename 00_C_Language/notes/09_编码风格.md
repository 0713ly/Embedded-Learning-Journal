# 1. 缩进和空白
C 语言的语法对缩进和空白没有硬性要求，空格、Tab、换行都可以自由书写。实现同样功能的代码可以排版得清晰易读，也可以写得杂乱难辨。
如果代码全挤在一起（缺乏空行和缩进），不仅阅读费力，也无法直观体现代码的逻辑层级，代码量超过一屏后可读性会急剧下降。

业界对 C 语言代码风格（Coding Style）有约定俗成的规范，主要分为**空格的使用**和**缩进与空行**两大部分。以下以 Linux 内核代码风格为基准进行总结。

## 1.1 空格的使用规则
1. **关键字与括号**：`if`、`while`、`for`、`switch` 等关键字与后面的控制表达式括号之间，插入一个空格分隔；但括号内部的表达式应紧贴括号。
   ```c
   while (1);
   ```

2. **运算符**：
   - **双目运算符**两侧各插入一个空格分隔，例如：`i = i + 1`
   - **单目运算符**和操作数之间不加空格，例如：`+i`、`!i`、`-x`、`&a[1]` 等

3. **后缀运算符**：操作数与运算符之间不加空格，例如结构体成员访问 `s.a`、函数调用 `foo(arg)`、数组元素访问 `a[i]`。

4. **标点符号**：`,` 和 `;` 之后要加空格（符合英文书写习惯），例如 `for (i = 1; i < 10; i++)`、`foo(arg1, arg2)`。

5. **优先级强调**：有时为了突出运算优先级，可以写得紧凑些（如 `distance = sqrt(x*x + y*y)`），但**绝不能**因为省略空格导致读者误解优先级（如 `a||b&&c` 容易造成优先级误判）。

6. **长语句折行**：接近或大于 80 个字符的长语句需要折行，折行后用空格与上方的表达式或参数对齐。
   ```c
   if (sqrt(x*x + y*y) > 5.0
       && x < 0.0
       && y > 0.0)
   ```

7. **长字符串拆分**：较长的字符串可以拆分成多个字符串分行书写，C 编译器会自动将相邻的多个字符串字面值拼接在一起。
   ```c
   printf("This is such a long sentence that "
          "it cannot be held within a line\n");
   ```

8. **变量对齐**：变量定义语句中，可以使用 Tab 字符对齐变量名，提升排版美观度（非强制要求）。

## 1.2 缩进与空行规则（内核风格）
1. **缩进使用 Tab 字符**：必须用 Tab 体现语句块的层级关系，**不能用空格代替 Tab**。在标准字符终端上 Tab 宽度为 8 个空格。混用空格和 Tab 会导致代码在不同编辑器下排版错乱。

2. **语句块大括号 `{` 的位置**：
   - `if/else`、`while`、`for`、`switch` 等带语句块的语句，**`{` 应该和关键字写在同一行**，用空格隔开（即 K&R 风格）。也有风格习惯让 `{` 独占一行，但同一项目内必须保持统一。
     ```c
     if (...) {
         语句列表;
     } else if (...) {
         语句列表;
     }
     ```
   - **例外**：**函数定义**的 `{` 必须独占一行。
     ```c
     int foo(int a, int b)
     {
         语句列表;
     }
     ```

3. **switch 语句格式**：`switch` 和语句块内的 `case`、`default` 左对齐（不额外缩进），但 `case` 下的语句列表需要向内缩进。自定义标号也应当顶格书写，不缩进。
   ```c
   switch (c) {
   case 'A':
       语句列表;
   case 'B':
       语句列表;
   default:
       语句列表;
   }
   ```

4. **空行分隔规范**：
   - **逻辑段落**之间（例如每个函数定义之间、头文件/全局变量/函数定义之间）应当插入一个空行分隔。
   - 函数内部的语句列表如果较长，可以根据逻辑相关性分成若干组，用空行分隔（通常变量定义块后加空行，`return` 语句前加空行）。

# 2. 注释
注释是代码可读性与可维护性的重要组成部分，规范的注释风格是工程素养的直接体现。

## 2.1 注释的格式
- **单行注释**：采用 `/* comment */` 的形式，注释界定符与文字之间用空格分隔。
- **多行注释**：工程中推荐标准格式：每行以 `*` 开头，上下对齐排列。也存在星号包围的装饰性格式，但团队项目开发中建议使用统一的标准格式。

## 2.2 注释的使用场合（6种核心场景）
1.  **源文件顶部注释**
    说明模块的基础信息，例如文件名、作者、功能描述、版本历史、版权声明等。**要求顶格书写，不缩进**。
    ```c
    /*
     * kernel/sched.c
     *
     * Kernel scheduler and related syscalls
     *
     * Copyright (C) 1991-2002 Linus Torvalds
     * ...
     */
    ```

2.  **函数注释**
    说明函数的功能、参数含义、返回值、错误码、注意事项等。**写在函数定义的正上方，和函数定义之间不留空行，顶格书写不缩进**。

3.  **相对独立的语句组注释**
    对一组逻辑关联的语句做整体说明。**写在语句组的正上方，和语句组之间不留空行，缩进层级与当前语句组保持一致**。

4.  **代码行右侧的简短注释**
    对单行代码做补充说明。一般使用单行注释，**代码与注释之间至少用一个空格隔开，多行并列的右侧注释建议上下对齐**。
    ```c
    offset = 0;                  /* uninitialised var warning */
    do {
        if (slot == NULL) {
            /* Have to add a child node.  */
    ```

5.  **复杂的结构体定义注释**
    结构体通常比函数更需要注释。结构体包含多个成员变量，需要对关键成员的作用、访问规则、并发约束等进行说明。

6.  **复杂的宏定义和变量声明注释**
    宏定义往往包含复杂逻辑或依赖特定硬件/架构，必须添加注释说明其设计意图与使用约束。

## 2.3 核心原则：尽可能少用注释
《Coding Style》中特别强调：**函数内部的注释要尽可能少用**。
- **注释的终极目标**：写注释主要是为了说明代码**「能做什么」**（例如函数接口定义），而不是为了说明**「怎样做」**。
- **好代码即好注释**：只要代码逻辑清晰、命名规范，「怎样做」本身就是一目了然的。如果需要大段注释才能解释清楚一段逻辑，说明代码本身可读性很差，此时应当优先重构代码，而非增加注释。
- **例外场景**：只有特别需要提醒注意的地方（例如反直觉的硬件Bug规避、特殊的并发死锁处理、严格的时序要求等），才需要在函数内添加注释。

# 3. 标识符命名
编写代码时，标识符（变量名、函数名、宏定义、类型名等）的命名是代码风格最基础的组成部分，直接决定了代码的可读性与专业度。命名应遵循以下核心原则：

## 3.1 原则一：清晰明了，善用缩写
命名应当准确表达语义。可以使用完整单词，也可以使用业界通用、易于理解的缩写：
- **短单词**：可通过去元音形成缩写，例如：`count` → `cnt`，`block` → `blk`，`length` → `len`，`window` → `win`，`message` → `msg`，`temporary` → `temp` / `tmp`
- **长单词**：可取单词头部几个字母形成缩写，例如：`number` → `num`，`transmit` → `xmt`
- **特殊缩写**：存在约定俗成的特殊缩写，例如 `internationalization` 缩写为 `i18n`（首尾字母 + 中间字母数量）

## 3.2 原则二：统一的命名风格（内核规范）
本书及 Linux 内核代码极力推崇**蛇形命名法（Snake Case）**，统一风格如下：
- **普通变量、函数、类型名**：采用**全小写 + 下划线**的方式命名。例如：`radix_tree_insert`、`struct radix_tree_root`
- **常量（宏定义、枚举常量）**：采用**全大写 + 下划线**的方式命名。例如：`RADIX_TREE_MAP_SHIFT`

### ? 强烈避坑：匈牙利命名法（Hungarian notation）
微软曾提出匈牙利命名法，在变量名中加前缀表示数据类型，例如 `iCnt`（前缀 `i` 表示 int）、`pMsg`（前缀 `p` 表示 pointer）。

Linus 在《CodingStyle》中对此明确反对：
> "Encoding the type of a function into the name (so-called Hungarian notation) is brain damaged - the compiler knows the types anyway and can check those, and it only confuses the programmer. No wonder MicroSoft makes buggy programs."  
> （把类型编码进变量名里是低效的做法，编译器本身就知道类型并且可以做检查，这种命名只会混淆程序员。难怪微软总写出有漏洞的程序。）

因此，**代码中绝不使用大小写混合的变量名，更不使用匈牙利命名法**，保持统一的蛇形命名风格。

## 3.3 原则三：根据作用域决定命名长度
- **全局变量与全局函数**：命名必须**详细清晰**，可以多用几个单词和下划线（例如 `radix_tree_insert`）。因为它们会在项目的多个源文件中被调用，必须让所有使用者明确其功能。
- **局部变量与内部函数**：命名可以适当简略，但不能过于简略导致语义不明。
- **单字母变量**：尽量避免使用单个字母作为变量名。**唯一公认的例外**：`i`、`j`、`k` 作为循环变量，是行业通用惯例。

## 3.4 原则四：针对中国开发者的特别提醒
**绝对禁止使用纯汉语拼音做标识符**。例如 `int nianling`（年龄）、`void xianshi()`（显示）这类写法可读性极差，在团队协作和专业面试中会严重减分。英语基础薄弱可以借助词典，实在不确定也优先用拼音+英文的组合，最规范的方式是使用标准英文命名。

### ? 嵌入式视角延伸
在嵌入式驱动开发中，你会经常看到 `HAL_GPIO_WritePin`、`vTaskDelay` 这类命名，这属于驼峰命名法或前缀命名法（例如 `v` 代表 void 返回，`x` 代表 portBASE_TYPE）。

虽然 Linux 内核不推崇这种风格，但 STM32 HAL 库、FreeRTOS 等嵌入式生态大量使用这类命名法。**你只需要记住一个黄金法则：同一个文件、同一个项目内，命名风格必须保持统一。** 千万不要在同一个 `.c` 文件里混用 `my_variable` 和 `myVariable` 两种风格，这会让接手代码的同事（或者面试官）体验极差。

# 4. 函数

每个函数都应该设计得尽可能简单，简单的函数才容易维护。在编写和设计函数时，应遵循以下原则：

## 4.1 核心原则：单一职责

**实现一个函数只是为了做好一件事情。**
不要把函数设计成用途广泛、面面俱到的“万能函数”。这种函数通常会写得超长，而且往往不可重用，维护起来极其困难。如果一个函数承担了多个任务，当需求改变时，很容易牵一发而动全身。

## 4.2 控制函数长度与缩进复杂度

*   **缩进层次**：函数内部的缩进层次不宜过多，一般**以少于 4 层为宜**。如果缩进层次太多（比如出现了多重嵌套的 `if-else` 或 `for` 循环），说明设计得太复杂了，应考虑分割成更小的函数（**Helper Function**，辅助函数）来调用。
*   **代码长度**：函数不要写得太长，建议在 24 行的标准终端上**不超过两屏**。如果超过两屏，会造成阅读困难，应考虑分割。
*   **局部变量数量**：另一种度量函数复杂度的办法是看它有多少个局部变量。**5 到 10 个局部变量已经很多了**，再多就很难维护了，应该考虑将其分割成多个函数。

## 4.3 特殊情况：概念简单，代码较长

《CodingStyle》中特别说明：如果一个函数在概念上是简单的，只是长度很长，这倒没关系。
例如，函数由一个大的 `switch` 组成，其中有非常多的 `case`（比如网络协议中的 TCP 状态机实现）。这是可以的，因为各个 `case` 分支互不影响，整个函数的复杂度只等于其中一个 `case` 的复杂度。

## 4.4 命名与注释规范

*   **命名体现动作**：执行函数就是执行一个动作，函数名通常应**包含动词**。例如：`get_current`、`radix_tree_insert`。
*   **必加注释**：比较重要的函数，定义上侧**必须加注释**，说明此函数的功能、参数、返回值、错误码等（参考前文的注释规范）。

---
### ? 嵌入式视角的延伸：
在单片机（STM32）开发中，**控制函数长度极其重要**。因为单片机的 RAM（栈空间）通常很小（可能只有几十KB甚至几KB）。如果一个函数内部定义了大量的局部变量、又有一层层深的函数嵌套调用，极其容易导致**栈溢出（Stack Overflow）**，导致程序死机（HardFault）。

另外，命名包含动词（如 `HAL_GPIO_WritePin`）是嵌入式库的标配。当你以后用 FreeRTOS 写多任务时，你的每个“任务函数”（Task）最好都是单一职责的，比如一个任务只负责读传感器，另一个任务只负责刷新屏幕，千万别揉在一个任务里。

# 5. indent工具

`indent` 工具可以自动把代码格式化成某种风格，例如把缺乏缩进和空白的代码格式化成内核编码风格。

## 5.1 基本用法与参数

运行 `indent` 命令时，常用的参数组合如下：
```bash
$ indent -kr -i8 main.c
$ cat main.c  # 查看格式化后的代码
```

*   **`-kr`**：选项表示 **K&R 风格**。
*   **`-i8`**：表示缩进 **8 个空格**的长度。
*   **`-nut`**（可选）：如果没有指定此选项，默认每 8 个缩进空格会自动用一个 **Tab** 代替。

> ?? **重要注意**：
> `indent` 命令会**直接修改原文件**，而不是打印到屏幕上或者输出到另一个文件。这一点和很多 UNIX 命令不同。

## 5.2 格式化效果与局限性

使用 `-kr -i8` 格式化出来的代码，已经很符合规范：添加了必要的缩进和空白，较长的代码行也会自动折行。

**局限性**：
工具**没有添加适当的空行**。因为 `indent` 工具不知道哪几行代码在逻辑上是一组的，空行还是需要自己动手添。当然，原有的空行肯定不会被 `indent` 删去。

## 5.3 使用建议

*   **推荐参数**：如果采纳标准内核编码风格，基本上 `-kr -i8` 这两个参数就够用了。具体其他选项可参考 `Man Page`。
*   **特定场景**：有时 `indent` 非常有用，比如某个项目中途决定改变编码风格（很少见），或者往项目中添加几个来自另一个编码风格不同项目的代码文件。
*   **开发铁律**：**绝不能因为有了 `indent` 工具就肆无忌惮**。一开始就应该认真把代码写好，避免写成乱七八糟的样子再依靠 `indent` 去清理。工具只是兜底，良好的编码习惯才是根本。
